# KVL 대회·선수 데이터 자동화 운영기준 v1

작성일: 2026-11-01. 요청 범위: 대회 추가부터 종료 후 보관까지의 운영 표준,
선수 명단·등록·이적·공식 공시 및 별도 기사 수집, 대학·중고 공식 첨부자료 처리.

상위 기준은 같은 문서 ID를 유지한
[KVL 운영원칙 MASTER v18](https://docs.google.com/document/d/1iu1aWoTdSf2L7VCco5X7pCPxs9qVlM9rskZ8_hI76FY/edit)이다.
특정 시즌의 실행·검증 상태는 이 문서의 원칙과 분리하여 STATUS와 validation 기록에 둔다.

## 1. 대회 추가의 완료 단위

**페이지 제작 + MASTER 연결 + 자동 업데이트 + 종료 후 기록 보관**을 하나의 운영 묶음으로 등록한다.
새 대회가 만들어졌다는 이유만으로 자료 수집이나 MASTER 쓰기가 자동 연결된 것으로 간주하지 않는다.

| 단계 | 필수 산출물 | 완료 판정 |
|---|---|---|
| 등록 | Competition_ID·시즌·성별·단계·담당자·공식 출처 | 기존 ID 및 다른 대회와 충돌 없음 |
| 페이지 | 공통 엔진 config/data, 기존 표준의 Hero·SEO·기능 | 실제 데이터·PC/모바일·필요한 인쇄 검수 |
| MASTER 연결 | 정확한 문서 ID·탭 ID·헤더·쓰기 허용 셀 범위 | 권한·ID 매칭·수식/잠금 보존·재조회 확인 |
| 자동 갱신 | 출처별 어댑터·검증기·실행 기간·주기·실패 처리 | 첫 실제 수집→MASTER→공개 데이터→배포 검증 |
| 종료 후 보관 | 공식 최종 확인·고정 스냅샷·출처·해시·게시 영수증 | 미해결 결과 없음, 모든 증거 및 원본 연결 일치 |

공통 생성기는 `config.json`, `data.json`, `operations.json`을 함께 만든다.
operations의 시작 상태는 `DRAFT`, 자동화는 비활성이다.

```sh
node scripts/scaffold-competition-v2.cjs --slug actual-event-slug
node scripts/scaffold-competition-v2.cjs --check data/competitions/actual-event-slug
node scripts/scaffold-competition-v2.cjs --check-operations data/competitions/actual-event-slug
node scripts/scaffold-competition-v2.cjs --ready-to-activate data/competitions/actual-event-slug
```

마지막 명령은 **운영 전환을 검토할 준비가 되었는지 확인하는 읽기 전용 검사**다.
외부 권한을 부여하거나 수집기·MASTER writer·예약 실행·보관 작업을 생성하지 않는다.
실제 어댑터와 workflow 연결, 운영자 승인 및 최초 실행 증거가 별도로 필요하다.
기존 config/data만 가진 대회의 페이지 검증은 호환성을 유지한다.

## 2. 기간과 상태

모든 자동화에는 담당자, 시간대, 시작 시각, 종료 시각, 실행 주기, 다음 검토 시점을 둔다.
신규 operations의 `startDate`·`endDate`는 해당 시간대의 날짜이며 종료일 하루를 포함한다.
runtime의 offset-aware `starts_at`·`ends_at`은 시작 포함·종료 미포함 구간이다.
예를 들어 KST 종료일 4월 29일을 포함하는 설정은 runtime 종료 경계 4월 30일 00:00과 같다.
어댑터를 연결할 때 이 변환을 검증하고 서로 다른 의미로 해석하지 않는다.
`archive.graceDays`는 갱신 종료 후 보관 검토에 배정한 기간이며 runtime의 실행 구간을
늘리지 않는다. 마지막 경기 후 정산 기간과 이 값을 합산하여 종료일을 다시 연장하지 않는다.

| 운영 상태 | 허용 동작 | 다음 전환 조건 |
|---|---|---|
| DRAFT / 준비 | 표본 수집·검수·연결 시험 | 출처·페이지·MASTER·기간·권한 검사 |
| 시작 전 | 읽기 검증, 필요 시 별도 승인한 일정/명단 준비 | 설정한 시작 시각 |
| UPDATING | 지원하는 대회 범위의 검증된 변경 반영 | 마지막 편성 경기 이후 최종 확인 기간 |
| RECONCILING | 누락·정정·최종 결과 대조 | 설정한 운영 종료 경계 |
| STOPPED_PENDING_ARCHIVE | 정기·수동 쓰기 중지, 미해결 사항 검토 | 공식 종료·결과·MASTER·배포·스냅샷 증거 |
| ARCHIVED | 읽기 제공, 버전을 남기는 정정 절차 | 새 시즌은 새 운영 묶음 |

기간이 끝났다고 연기·미완료 경기를 종료로 바꾸지 않는다. 날짜 도달과 공식 종료는 별개다.
공식 일정 변경이 갱신 구간을 벗어나면 자동 연장하지 않고 근거 확인 후 정책을 개정한다.
하나의 시즌에 정규리그·준플레이오프·플레이오프·챔피언결정전이 포함되면 공식 일정과
운영요강을 확인하여 마지막 가능 결승 경기까지를 기본 지원 범위로 등록한다.
기간 연장과 함께 단계별 수집·MASTER 연결·진출 조건·시리즈 조기 종료를 검증한다.
정규리그만 완료된 상태를 시즌 종료로 표시하지 않는다. 조건부 준PO 미개최와 시리즈
조기 종료 후 잔여 차전은 규정과 검증된 결과에 따라 미실시로 구분하고 0:0 결과를 만들지 않는다.
컵대회와 다음 시즌은 각각 별도의 지원 범위·형식·운영 묶음을 확인한다.
예외적인 정정 재개는 새 기간·사유·담당자를 기록하며 과거 시각을 주입하여 마감을 우회하지 않는다.

GitHub의 예약 실행은 정확한 초·분의 실행이나 누락 없는 실시간 중계를 보장하지 않는다.
누락 시 다음 실행에서 지원 범위를 다시 대조한다. 공개 저장소의 예약 workflow는 저장소 활동이
60일 동안 없으면 비활성화될 수 있으므로 실행 이력과 마지막 정상 갱신 시각을 확인한다.
근거: [GitHub schedule 문서](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).

## 3. 검증된 반영 경로

1. 공식 공지와 첨부파일을 읽고 Source_ID·원문 URL·게시 시각·수집 시각·SHA-256을 기록한다.
2. 변경 후보를 생성한다. 같은 URL의 파일 교체나 공시 정정도 다른 원문 버전으로 구분한다.
3. 대회/팀/선수 ID, 시즌·성별·단계, 경기 수·점수·순위·규정·중복·단위를 검증한다.
4. 애매한 신원·효력일·원문 충돌·OCR 값은 검수 대기로 둔다. 이전 확정값을 유지한다.
5. MASTER를 최신 상태로 다시 읽고 허용 범위만 변경한다. 수식·수동 잠금·검증 규칙을 보존한다.
6. MASTER 재조회를 확인한 뒤 공개 가능한 필드만 사이트 데이터로 만든다.
7. 데이터 커밋, Pages 빌드 SHA, 실제 공개 파일 내용을 대조하여 게시 완료를 기록한다.

MASTER 쓰기와 GitHub 배포는 하나의 트랜잭션이 아니다. 부분 성공을 사실대로 기록하고
다음 실행에서 나머지 단계를 복구한다. 이미 정확히 반영된 MASTER를 무조건 롤백하지 않는다.
실패 보고에는 실행 링크·정제한 이유·영향 범위만 남기며 인증값·비공개 원문을 넣지 않는다.
동일 오류는 기존 중복 방지 경로를 사용한다.

## 4. 선수 명단·등록·이적·공시

선수 정보는 현재 명단과 사건 이력으로 분리한다. 대회 당시 최종 명단은 별도 스냅샷이다.
등록·해지·이적·임대·복귀·은퇴·등번호/포지션 정정은 독립된 사건으로 보관한다.

필수 연결은 기존 Player_ID, 시즌·성별·팀, 공시 ID·URL·원문 버전,
게시일·수집일·효력일, 변경 전후 값, 검수자·검수 시각이다.
이름만으로 ID를 추정하거나 새 ID를 만들지 않는다. 공식 식별자 또는 검수된 신원 근거를 사용한다.
부분 공시에서 보이지 않는 선수를 자동으로 미등록·퇴단으로 바꾸지 않는다.
임대 만료만으로 원팀 등록을 되살리지 않으며 별도 재등록 근거를 확인한다.

공식 출처 수집과 후보 생성은 자동화한다. 신원·효력일 검토는 해당 **원문 버전**에 연결한다.
원문이나 파서 해석이 정정되면 과거 승인을 재사용하지 않는다.
명단 스냅샷의 공시일을 선수 입단일·등록 시작일로 사용하지 않는다.

2026-11-03 승인된 **현재값 확인 기록**은 효력일이 확정된 변경 사건과 별도로 운영한다.
기존 ID와 공식 현재명단·공시가 일치한 번호·포지션을 관측한 사실을 기록할 수 있지만,
공시일·관측일을 미확인 효력일로 채우지 않는다. 최초 검증은 오재성 한 명의 이미 같은
등번호를 별도 `KVL_현재값확인` 탭에 저장·재조회하는 범위다. 선수 셀 수정, 등록·이적·해지
판단, 대회 당시 명단 재구성은 이 기록으로 수행하지 않는다. 정책과 실제 native/GitHub 실행
상태는 [현재값 확인 기준](proposals/player-current-value-policy-v1.md)과
[첫 검증 기록](validation/player-current-value-20261103.md)으로 구분한다.

선수 공시의 운영 기간은 경기 업데이트 기간과 별도로 관리한다. 비시즌 이적·등록도 감시하되
현재 시즌 입력 경로를 다음 시즌 자동 지원으로 표현하지 않는다. 연중 감시에도 명시적인
운영 종료/다음 시즌 검토 시점을 두고 새 시즌 설정을 확인한다.

구현·검수 기록: [선수 업데이트 v1](KVL_PLAYER_UPDATES_v1.md).
검토 완료 export와 실제 MASTER 적용 상태를 구분하고, 쓰기 연결이 없으면 `NOT_CONNECTED`로 표시한다.

## 5. 기사 수집

공식 공시와 별도의 기사 목록을 수집할 수 있다. 제공자의 RSS·허용 API에서
제목·언론사·원문 링크·게시 시각·최초 발견 시각을 보관한다.
선수/대회 연결이 확인되지 않았으면 후보로 유지한다. 기사 본문·사진을 일괄 복제하지 않는다.
이적설, 예정, 보도 내용은 공식 선수 MASTER의 확정 사실로 자동 승격하지 않는다.

초기 제공처는 [매일경제 RSS](https://www.mk.co.kr/rss)와
[뉴시스 RSS](https://www.newsis.com/RSS/index.php)다. 스포츠 피드의 최근 항목과
배구 관련 제목 키워드를 대상으로 하므로 모든 배구 기사를 빠짐없이 수집한다고 보장하지 않는다.
동일 URL·원문 버전 중복을 제거하고, 한 피드 장애는 공식 공시 및 경기 수집과 분리한다.
새 API·유료 공급자·공개 기사 페이지 연결은 별도의 설정·검토 범위다.

## 6. 대학·중고의 공식 PDF·엑셀·이미지

파일 기반 처리도 가능하다. 다만 실제 해당 대회의 자료로 추출·ID 매칭·검증을 통과한
어댑터만 자동 반영에 사용한다. 파일을 열 수 있다는 결과와 운영 자동화 성공은 구분한다.

| 형식 | 추출 방식 | 반드시 검토할 항목 |
|---|---|---|
| 텍스트 PDF | 문자·표 추출, 페이지/행 연결 | 병합 셀, 반복 헤더, 읽기 순서, 조·장소 충돌 |
| 스캔 PDF·이미지 | OCR → 후보 생성 | 이름·숫자·점수·행 오인식, 원본 이미지 대조 |
| XLS/XLSX | 시트·셀·값·형식 읽기 | 다중 시트, 병합, 수식 결과, 숨은 행, 날짜·단위 |
| HTML 표 | 공식 표의 행·열 정규화 | 병합 날짜, 약칭, 미정 대진, 수정 공지 |

서버의 MIME만으로 형식을 판정하지 않는다. 파일 헤더와 실제 파서 열기 결과를 확인한다.
원본의 페이지 또는 시트·셀 위치를 보존한다. 표 범위 밖으로 병합 값의 이어받기를 확대하지 않는다.
순위는 해당 대회 규정에 따라 계산하며 다른 대회의 승점/승자승 규칙을 가져오지 않는다.

공개 export는 이름·팀·공개 경기 사실 등 필요한 필드만 선택한다.
신청서에 들어 있는 전화번호·주소·계정정보 등은 공개 후보 데이터에 포함하지 않는다.
공식 파일은 기존 Drive 원본 보관 위치에 보존하고 GitHub에는 출처·해시·정규화 결과를 둔다.

실물 검증과 한계: [공식 파일 처리 가능성 검증](validation/academic-source-feasibility-20261101.md).
대학 동아리 참가신청서와 엘리트 대학·중고 등록명단은 별개의 근거다.

## 7. 종료 후 보관과 정정

대회별 보관 위치·담당자·절차는 등록 시 정한다. 실제 완료 판정에는 다음 증거가 필요하다.

- 공식 최종 결과와 종료 근거; 미해결·연기 경기 및 원문 충돌 처리.
- 전체 대상 경기·순위·대회 당시 명단의 최종 상태.
- MASTER 쓰기·재조회 결과와 공개 데이터 검증.
- 배포 커밋·빌드 SHA, 실제 공개 JSON의 바이트 및 정규화 내용 해시.
- 기존 원본 연결, 고정 스냅샷 파일별 SHA-256, 검증 시각과 변경 이력.

하나라도 빠지면 `STOPPED_PENDING_ARCHIVE`다. 자동 종료 시점에 `ARCHIVED`를 미리 붙이지 않는다.
완료된 시즌의 명단을 현재 이적 정보로 덮어쓰지 않는다.
공식 사후 정정은 이전 버전을 보존하고 새 버전·정정 근거·담당자를 남긴다.

### 현재 V-리그 보관 준비 명령

최종 공식 종료 검수 자료와 마지막 성공한 게시/배포 영수증을 확보한 뒤 실행한다.

```sh
python -B scripts/kvl_competition_lifecycle.py prepare-archive \
  --root . \
  --official-completion /path/official-completion.json \
  --publication-receipt /path/report.json \
  --deployment-receipt /path/deploy.json
```

이 명령은 검증한 공개 파일·정제한 영수증·해시 manifest만 새 로컬 archive에 준비한다.
진행 중 시즌, 증거 누락, 기존 보관 폴더가 있으면 실패하며 덮어쓰지 않는다.
성공 상태는 `ARCHIVE_PREPARED_NOT_ACTIVATED`이고 정책 포인터 변경안을 출력한다.
config·Google·GitHub를 자동 변경하지 않는다. 준비 파일과 정책 변경을 검토·반영한 뒤
동일 validator로 `ARCHIVED` 판정을 확인한다. 현재 시즌은 미완료이므로 이 명령이 거부되는 것을 검증했다.

이 기존 V-리그 어댑터는 `data/automation/archive/{automation_id}/`를 사용한다.
신규 starter의 `data/archive/.../<slug>/` 계획과는 별도의 명시적 경로 계약이며,
operations 파일만 추가하여 기존 어댑터를 자동 연결하거나 보관 위치를 바꾸지 않는다.

## 8. 현재 구현과 운영 전환의 구분

| 기능 | 이번 변경의 범위 |
|---|---|
| 기존 V-리그 경기 수집 | 최초 실제 MASTER·게시 성공은 별도 확인 완료; 기존 운영 유지 |
| 실행 종료일 | 남녀 정규리그~챔피언결정전 + 최종 대조 7일; 2027-04-30 00:00 KST부터 쓰기 중지 |
| 선수 공시·기사 | 버전별 후보와 검토 export, 메타데이터 수집; 미확정 선수 사실 자동 게시 없음 |
| 새 대회 생성 | 운영 manifest와 준비 검사 추가; 출처 어댑터·외부 연결 자체를 자동 생성하지 않음 |
| 파일 자료 | 실물 PDF 표·XLSX 구조 파싱 검증; 미확보 실제 중고/엘리트 결과 표본은 별도 검수 |
| 종료 보관 | 증거·해시 검증 계약 및 절차; 현재 진행 중 시즌을 보관 완료로 표시하지 않음 |

운영 merge·배포 상태는 [이번 변경의 검증 기록](validation/competition-automation-extension-20261101.md)에서 확인한다.
